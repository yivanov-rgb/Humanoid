# Правила проекта Humanoid

## Режим работы

- Обсуждение: отвечай на вопросы без изменений проекта.
- Исследование и ревью: читай файлы, анализируй diff и выполняй безопасную диагностику; найденные проблемы автоматически не исправляй.
- Планирование: предложи изменения и порядок работ; реализация требует запроса пользователя.
- Реализация: выполняй явно запрошенные изменения в согласованных границах. Существенное расширение архитектуры сначала обсуди.
- Обсуждение решения само по себе не разрешает реализацию. При существенной неоднозначности уточни намерение; до уточнения работай только на чтение.
- Делегирование не расширяет полномочия и объём задачи.

## Объём работы и структура

- Перед работой прочти применимые AGENTS.md, проверь ветку и Git status. Другую документацию открывай по необходимости для текущей задачи.
- Сначала определи минимальный набор нужных файлов. Используй целевой поиск; расширяй исследование по обнаруженным зависимостям и рискам.
- Используй уже полученный контекст; не перечитывай неизменившиеся файлы без конкретной причины и не исследуй весь репозиторий ради знакомства.
- Предпочитай минимальные изменения существующей реализации. Сохраняй архитектуру, интерфейсы, стиль и именование; избегай несвязанного рефакторинга и форматирования.
- Перед созданием файла проверь существующие реализации. Новые файлы, каталоги, зависимости и абстракции требуют конкретной необходимости.
- Не создавай резервные или альтернативные копии скриптов. Перед удалением или переносом проверь зависимости.
- Не добавляй инструкции и отчёты для каждой небольшой задачи. Актуальные команды хранятся в robot/README.md и simulation/README.md, сведения об ActionGroups — в simulation/ACTION_GROUPS_RU.md; историю изменений сохраняет Git.
- Исходники сценариев физического робота находятся в robot/. Корневые tag_grab.py и line_follow.py — совместимые символические ссылки; не заменяй их копиями.

## Архитектура и совместимость

- Сохраняй разделение управления физическим роботом, восприятия, навигации, тестов и симуляции. Настройки симуляции не переносить на робот автоматически.
- Не смешивай ROS 1 и ROS 2 API, пакеты, launch-форматы и системы сборки без согласованного решения.
- Перед изменением интерфейса проверь вызовы и зависимости. Сохраняй ROS-топики, сервисы, действия, сообщения, параметры, пространства имён и системы координат, если задача не требует их изменения.
- Не меняй рабочую калибровку, модель, контроллеры, параметры движения, физику и поведение других компонентов без необходимости для задачи.

## ActionGroups и физический робот

- По подтверждению пользователя все исходные ActionGroups, полученные напрямую с робота, достоверны и проверены. Используй их через MotionManager.run_action без повторной проверки безопасности и диапазонов сервоприводов.
- При разделении или изменении ActionGroups проверяй внесённые изменения: нужные сервоприводы, сохранность значений, кадров, порядка, таймингов и совместимость формата.
- Перед новыми прямыми командами сервоприводам проверяй подтверждённые механические пределы каждого ID. Протокольные 0..1000 и пределы URDF не заменяют механические пределы; при неизвестных пределах ограничься чтением и наблюдением.
- Запускай физические движения только в рамках разрешённой задачи. Успех в симуляции сам по себе не подтверждает результат на роботе.
- Перед испытанием свободной ходьбы подготовь и проверь начальную позу модели на полу. Снятие подвеса само по себе недостаточно.
- Для ходьбы по линии с GUI используй --free. Режим --anchored предназначен для отдельно обозначенной диагностики интерфейсов и не заменяет свободную ходьбу.

## Проверки

- Выбирай минимальную проверку, достаточную для внесённого изменения. Для документации обычно достаточно проверки ссылок, команд и diff; для преобразования данных — формата и изменённых данных.
- Используй существующие инструменты и целевые тесты. Полный набор тестов, контейнер, smoke, Gazebo и GUI запускай только по запросу или когда конкретное изменение требует такой проверки; объясни её необходимость.
- После успешной достаточной проверки переходи к завершению задачи. Повторяй или расширяй проверки при новых изменениях, ошибках или нерешённом риске.
- Постоянные тесты добавляй для полезного повторяемого покрытия и предотвращения регрессий. Не создавай временные скрипты и новые тестовые фреймворки для одноразовой проверки.
- Сообщай только фактически выполненные проверки. Различай проверку исходников, симуляцию и физическое испытание; обозначай существенные ограничения.

## Процессы и очистка

- Отслеживай процессы и контейнеры, запущенные для задачи. По завершении останавливай свои GUI, ROS-узлы, тесты и стенды; для испытаний используй finally или shell trap, где уместно.
- Проверяй завершение запущенных тобой процессов существующими средствами, без дополнительных запусков ради очистки.
- Посторонние процессы не останавливай. Оставшийся humanoid-ainex-sim останавливай только после подтверждения его принадлежности предыдущей работе агента.
- Не определяй принадлежность только по имени процесса. Если она неясна, не останавливай процесс автоматически и укажи ограничение.
- Не удаляй контейнеры, образы, тома и данные, если достаточно остановки.

## Git Workflow

- Основная ветка — master. Разработка и самостоятельное слияние в master запрещены.
- Перед изменениями выбери подходящую рабочую ветку или создай её, сохранив незавершённые пользовательские изменения. Используй название по задаче, например feature/line-follow.
- Один агент владеет не более чем одной активной рабочей веткой. Перед новой задачей заверши или передай предыдущую; не создавай дополнительные ветки для параллельных задач одного агента.
- Работай только в назначенном worktree и ветке. Для независимых параллельных изменений используй изолированные worktree; не переключай ветки в чужом рабочем дереве.
- Не перезаписывай, не отменяй и не теряй чужие изменения. Разрушительные Git-операции и изменение опубликованной истории требуют явного разрешения пользователя.
- Допустимы логически связанные коммиты своей задачи. Перед коммитом проверь staged diff на посторонние изменения.
- Синхронизация рабочей ветки с master допустима при необходимости и сохранности чужой работы; не разрешай сомнительные конфликты автоматически.
- Создание PR в master и решение об интеграции остаются пользователю. Подготовка ветки не означает её интеграцию.
- Не удаляй рабочую ветку без разрешения пользователя.

### Reviewer

Reviewer читает код, зависимости и diff, выполняет безопасные проверки в назначенном worktree и сравнивает с целевой веткой, обычно master. Он не изменяет файлы, индекс и историю, не создаёт коммиты/PR, не создаёт, не переключает, не сливает и не удаляет ветки, не запускает физические движения. Исправления выполняет Developer. В замечаниях нужны конкретные факты, последствия, серьёзность и привязка к файлу/кадру; если проблем нет, сообщи об этом и укажи ограничения проверки.

## Завершение задачи

Проверь итоговый diff и Git status: соответствие запросу, отсутствие лишних файлов, дублирования и потери чужих изменений. Кратко сообщи результат, затронутые/новые файлы, ветку и коммиты, выполненные проверки, непроверенные области и оставшиеся проблемы, состояние незакоммиченных изменений. Для подготовленной интеграции укажи готовность к ревью и созданию PR пользователем. Не перечисляй подробно рутинные действия.
