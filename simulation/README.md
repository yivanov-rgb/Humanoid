# Локальный стенд AiNex: ROS Noetic и Gazebo 11

Скрипты для физического робота находятся в [robot/](../robot/README.md). В корне сохранены совместимые ссылки `tag_grab.py` и `line_follow.py`; аппаратная калибровка не менялась.

[Очистка проекта и восстановление резервных действий](CLEANUP_RU.md): рабочие данные сохранены, лишние распакованные копии и кэши удалены.

**GUI и ручные движения:** [пошаговая инструкция](MANUAL_DEBUG_RU.md). Запуск окна: `bash simulation/sim.sh gui`; доступные ActionGroups: `bash simulation/sim.sh list-actions`; движение: `bash simulation/sim.sh action stand`.

**Ручная отладка линии:** [пошаговая инструкция](LINE_FOLLOW_RU.md). Девять реальных действий подготовлены в `simulation/actiongroups`. Актуальные проверки выполнены на хосте; состояние симуляционного прогона приведено ниже. Кубы удалены, линия заменена пологой дугой. Последний свободный GUI-прогон **не пройден**: после начала девятого действия защитная остановка при удалении от дуги на 8 см. Старый результат 75 см относится к прежнему контроллеру на прямой. Маршрут А→Б пока не подтверждён. [Запуск на реальном роботе](../robot/LINE_TEST_RU.md). [Результаты и ограничения](TEST_RESULTS_RU.md), [инвентаризация действий](ACTION_GROUPS_RU.md).

Стенд предназначен для цикла **гипотеза → минимальная реализация → автоматические проверки → Gazebo → отладка → контролируемое испытание на роботе**. Рабочий `tag_grab.py` и его калибровка не меняются при подготовке среды.

## Состав среды

| Компонент | Назначение |
|---|---|
| `.venv` на хосте | Лёгкие регрессионные тесты Python без ROS, сторонних пакетов и движений; используется Python хоста |
| Локальный Docker-образ `humanoid-ainex:noetic-gazebo` | Ubuntu 20.04, ROS1 Noetic, Gazebo Classic 11 и системные библиотеки |
| `/opt/ainex-venv` внутри образа | Python 3.8, `--system-site-packages`, доступ к ROS/OpenCV из APT |
| `/opt/ainex_ws` внутри образа | Catkin workspace с официальной моделью AiNex и пакетом `robotrio_sim` |
| `simulation/artifacts/` | Результат smoke-проверки, снимок камеры, журнал запуска |

`venv` не устанавливает ROS/Gazebo как системные компоненты. На текущем хосте Ubuntu 26.04/Python 3.14 они вынесены в Focal-контейнер, соответствующий целевой среде Noetic. [Целевые платформы Noetic: REP 3](https://github.com/ros-infrastructure/rep/blob/master/rep-0003.rst#noetic-ninjemys-may-2020---may-2025), [официальный Dockerfile OSRF](https://github.com/osrf/docker_images/blob/master/ros/noetic/ubuntu/focal/desktop-full/Dockerfile).

Noetic и Gazebo Classic завершили стандартный срок поддержки в 2025 году. Здесь эта связка используется для совместимости с существующим ПО робота. Образ ROS использует подписанный [финальный snapshot Noetic](https://github.com/osrf/docker_images/blob/master/ros/noetic/ubuntu/focal/ros-core/Dockerfile); подписи APT не отключаются. [Статус Gazebo Classic](https://classic.gazebosim.org/).

Модель берётся из `Hiwonder/ainex` на фиксированном commit из `vendor.lock`; скачанная копия игнорируется Git. Подготовленный проект не изменяет соседний ROS2-проект `robotrio`.

## Первичная подготовка

Из корня `Humanoid`:

```bash
python3 -m venv --without-pip .venv
bash simulation/sim.sh fetch
bash simulation/sim.sh build
```

Хостовый venv использует только стандартную библиотеку и поэтому не требует `pip`. Это не venv для выполнения ROS Noetic. В контейнере полноценный venv создаётся Python 3.8 вместе с `pip`; дополнительные зависимости следует фиксировать в Dockerfile и пересобирать образ. Хостовый `.venv` в образ не копируется.

Для Docker нужны права доступа к локальному daemon; скрипты не изменяют группы пользователя, Docker socket или системные пакеты хоста. Первая сборка скачивает крупный базовый образ и APT-зависимости.

## Проверка среды

```bash
bash simulation/sim.sh test
bash simulation/sim.sh test-container
bash simulation/sim.sh smoke
```

Первая команда проверяет регрессии `tag_grab.py` без ROS и приводов. Вторая выполняет те же проверки в целевом Python 3.8. Они проверяют независимость порогов рук, отбор нужного ID, свежесть кадров, порядок действий и прекращение последовательности при исключении; они не подтверждают физический захват.

Smoke-проверка запускает настоящий `gzserver` с виртуальным дисплеем Xvfb и программным рендерингом Mesa. Она проверяет модель AiNex, продвижение `/clock`, контроллеры, состояния суставов, изображение камеры и отклик сустава головы. Код завершения 0 означает прохождение этих проверок. JSON и журнал сохраняются в `simulation/artifacts/`; наличие отчёта само по себе не означает успех — проверять поле результата.

## Интерактивная работа в ROS

```bash
bash simulation/sim.sh up
bash simulation/sim.sh shell
```

Внутри контейнера окружение уже подключено:

```bash
python --version
rosversion -d
dpkg-query -W gazebo11
rostopic list
rostopic echo -n 1 /joint_states
rosservice call /controller_manager/list_controllers "{}"
```

Команда `up` запускает контейнер без графического клиента, но с настоящим рендерингом камеры через Xvfb. Для окна Gazebo использовать `gui` или `up --gui` из локального X11/XWayland-сеанса. Авторизация передаётся приватной копией cookie, без `xhost +`. Подробнее — в инструкции ручной отладки.

Завершение:

```bash
exit
bash simulation/sim.sh logs
bash simulation/sim.sh stop
```

Симулятор запускается как `humanoid-ainex-sim`, отдельно от контейнера физического робота `ainex`. Используются `--network none`, ROS на loopback, без host networking, проброса устройств или privileged-режима. Проект доступен внутри только для чтения; результаты записываются в отдельную папку artifacts. Команды физическому роботу из этого стенда не отправляются.

Собственный пакет `robotrio_sim`, `tag_grab.py` и тесты подключаются bind mount только для чтения. Изменения Python, launch и мира доступны при следующем запуске без пересборки. После изменения зависимостей, CMake, Dockerfile или официальной модели выполнить `build`.

## Что можно проверять сейчас

Режим `up/gui` по умолчанию — **свободная модель**. Неподвижное крепление включается только флагом `--anchored`; smoke включает его явно. Мир по умолчанию содержит плоский пол и чёрную линию шириной 30 мм: дугу длиной 2 м, радиусом 6 м, с поворотом примерно на 19°. Кубы удалены из файла сцены и при новых запусках не появляются. AprilTag и объекты захвата в текущем мире отсутствуют.

Важные границы модели:

- В исходном репозитории Hiwonder `kinematics.so` и `walking_module.so` собраны под ARM aarch64. Их нельзя непосредственно загрузить в x86_64-контейнере. Поэтому здесь не запускаются процедурная походка и аппаратный `ainex_controller.launch`.
- В исходной модели камера закреплена на корпусе. Overlay переносит её на `head_tilt_link`: положение головы теперь меняет изображение. Оптическая привязка и вынос камеры перед сеткой головы являются условной геометрией стенда. При tilt=260 корпус перекрывал полезный обзор; выбранное для симуляции 300 оставляет линию в рабочих ROI. Это не измерение и не безопасный диапазон физической камеры/сервопривода.
- Ручной проигрыватель использует официальный `MotionManager` и симуляционный адаптер pulse→rad с длительностями кадров, проверкой ограничений и остановкой. Это позволяет запускать `.d6a` без ARM-библиотек процедурной ходьбы. Полный `tag_grab.py` ещё требует подключения AprilTag-конвейера и проверки сценария.
- Девять действий для линии скопированы в стандартный `simulation/actiongroups`, полностью проверены и проиграны на креплении. Источник всех 48 действий сохранён в `simulation/artifacts/d6a_from_robot/home/ubuntu/software/ainex_controller/ActionGroups`. Из 48 основных действий 12 имеют статически обнаруженные расхождения с ограничениями модели — см. инвентаризацию; они в выбранный набор не включены. Подрезать pulse ради симуляции нельзя.
- Для проверки AprilTag нужно добавить реальные метки с верной геометрией, собрать Hiwonder-детектор с `corners` и согласовать топики камеры. Upstream камера публикует `/camera/image_raw`, тогда как некоторые готовые примеры ожидают `/camera/image_rect_color`.
- Контакты захвата, трение, усилия и динамика двуногой ходьбы ещё не откалиброваны. Смоделированное движение не заменяет проверку удержания кубов и устойчивости на роботе.

## Порядок каждого эксперимента

1. Записать гипотезу, наблюдаемое поведение и измеримый критерий успеха.
2. Зафиксировать исходную версию кода, конфигурацию, seed/позы сцены и необходимые ActionGroups. Сохранить рабочую калибровку реального робота.
3. Внести одно минимальное изменение в существующий компонент. Сначала прогнать офлайн-регрессии и тесты в Python 3.8.
4. Запустить smoke среды, затем отдельный сценарий Gazebo. Сохранить JSON, ROS-журнал/rosbag, изображения и результат критерия. Не считать smoke проверкой поведения, которого в нём нет.
5. При неудаче изменить одну причину и повторить тот же сценарий. Отдельно учитывать ограничения модели.
6. После успеха подготовить конкретную команду испытания на физическом роботе. Проверить текущее состояние камеры/ROS, начать с наблюдения и коротких действий, затем выполнить полный тест с возможностью остановки.
7. Сравнить симуляцию и робот, зафиксировать расхождения; только после этого считать гипотезу подтверждённой для устройства.

Девять выбранных `.d6a` уже проверены через проигрыватель и скрипт линии на креплении. Перед свободными тестами автоматически подготавливается и проверяется стойка stand. Далее нужно проверить шаги и подключить AprilTag-конвейер, сохранив `tag_grab.py`, ID, CLI и откалиброванные пороги.

## Проверка линии 18 октября 2026 года

После первоначального падения исправлены подготовка стойки, оси плеч и тип приводов. Историческая версия с одними поворотами прошла серию 30 действий и 8 проверок остановок на прямой. Аппаратные вызовы теперь используют штатный MotionManager без проверки диапазонов. На новой дуге после начала девятого действия сработала защита по расстоянию от линии — 8 см. Следование дуге и прибытие к AprilTag Б пока не подтверждены. [Полные результаты](TEST_RESULTS_RU.md), [ручная отладка](LINE_FOLLOW_RU.md). Команды `line-view` и `line-stop` позволяют открыть картинку и остановить маршрут с хоста.

## Начальная стойка и завершение процессов

Свободная модель создаётся сразу в позе `stand.d6a`, с опущенными руками и подошвами на полу. Приводы используют момент через `EffortJointInterface` и PD-регуляторы с демпфированием; прямое изменение положения суставов заменено. Настройки относятся только к симуляции и не являются калибровкой реальных сервоприводов.

Движения разрешаются после `initial_pose_ready: true`; состояние показывает `bash simulation/sim.sh status`. Подготовка проверяет также самопроизвольное смещение (>10 мм) и вращение (>3°); при нарушении допуска физика ставится на паузу. Независимая проверка стойки строже: 5 мм и 1° за 5 секунд симуляции. [Порядок запуска проверок](LINE_FOLLOW_RU.md#перед-свободными-тестами-начальная-стойка).

После работы выполнять `bash simulation/sim.sh stop`. Агент обязан завершить все свои процессы и контейнеры; правило сохранено в `AGENTS.md`.
