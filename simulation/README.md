# Локальный стенд AiNex: ROS Noetic и Gazebo 11

[Сценарии физического робота](../robot/README.md) и
[справочник ActionGroups](ACTION_GROUPS_RU.md) описаны отдельно.
Все команды ниже выполняются из корня Humanoid на локальном компьютере.
Симуляцию запускает и перезапускает пользователь вручную. Агент не запускает
Gazebo, GUI, smoke или другие сценарии, поднимающие симуляцию, даже для проверки
изменений; он готовит команды и анализирует переданные пользователем результаты.
Стенд `humanoid-ainex-sim` изолирован от аппаратного контейнера `ainex`:
сеть отключена, устройства робота не подключаются, проект монтируется только
для чтения, результаты записываются в `simulation/artifacts/`.

## Подготовка перед первым запуском

Среда контейнера: Ubuntu 20.04, ROS 1 Noetic, Gazebo Classic 11,
Python 3.8 в `/opt/ainex-venv` с ROS/OpenCV из системных пакетов.
ARM-библиотеки процедурной походки из штатного AiNex на x86_64 не запускаются;
для дискретных `.d6a` используется адаптер pulse→rad.
Модель HiWonder закреплена в `vendor.lock`, локальная копия — `simulation/vendor`.

Нужны Git, установленный и запущенный Docker
с доступом текущего пользователя к daemon. Откройте терминал на локальном
компьютере и выполните команды по очереди. Если проект находится в другом
каталоге, замените путь в `cd`.

```bash
cd /home/yor/projects/Humanoid
docker info
bash simulation/sim.sh fetch
bash simulation/sim.sh build
```

Если `docker info` завершился ошибкой подключения или доступа, сначала
устраните её; к сборке переходите после успешного выполнения команды.
Первая сборка скачивает образ и зависимости; скрипты не изменяют Docker socket,
группы или пакеты хоста.
Пересборка нужна при изменении зависимостей, Dockerfile, CMake или vendor-модели.
Python, launch и мир подключены из проекта и доступны при следующем запуске.

## Ручной запуск и остановка

1. Откройте терминал в локальном графическом сеансе и перейдите в проект.
   Проверьте, нет ли контейнера от предыдущего запуска:

   ```bash
   cd /home/yor/projects/Humanoid
   docker ps -a --filter 'name=^/humanoid-ainex-sim$' --format 'table {{.Names}}\t{{.Status}}'
   ```

   Если вывод содержит только заголовок, стенд ещё не создан. Если контейнер
   остался от вашего предыдущего опыта, выполните `bash simulation/sim.sh stop`
   перед новым запуском, даже если он уже остановлен. Чужой стенд не останавливайте.

2. Запустите окно Gazebo со свободной моделью на полу:

   ```bash
   bash simulation/sim.sh gui --free
   ```

   Команда печатает режим `FREE` и ID контейнера, затем возвращает терминал.
   Gazebo продолжает работать в контейнере; появление окна ещё не означает
   готовность модели к движению.

3. Проверьте готовность начальной стойки:

   ```bash
   bash simulation/sim.sh status
   ```

   Дождитесь `initial_pose_ready: true` и пустого `initial_pose_error`.
   Если ROS ещё недоступен или готовность равна `false`, повторите команду
   после загрузки. При непустом `initial_pose_error` посмотрите
   `bash simulation/sim.sh logs`: подготовка не удалась, физика ставится
   на паузу. К ходьбе в таком состоянии не переходите.
   После готовности можно вручную запускать действия или
   [проверку камеры и следования линии](#камера-и-следование-линии).

4. По окончании опыта остановите стенд:

   ```bash
   bash simulation/sim.sh stop
   docker ps -a --filter 'name=^/humanoid-ainex-sim$' --format 'table {{.Names}}\t{{.Status}}'
   ```

   После успешной остановки вывод второй команды содержит только заголовок.
   `stop` закрывает GUI/ROS-процессы, останавливает и удаляет контейнер стенда,
   удаляет его приватную копию Xauth. Закрытия окна Gazebo недостаточно.

Для запуска без окна вместо шага 2 выполните `bash simulation/sim.sh up --free`:
это headless Gazebo с Xvfb. `gui` (или `up --gui`) открывает окно в локальном
X11/XWayland-сеансе. Для GUI нужны `DISPLAY`, доступный X-сокет и утилиты
`xauth`, `xdpyinfo`, `timeout`. Используется приватная копия Xauth-cookie;
`xhost +`, privileged и host networking не нужны. SSH X-forwarding не поддерживается.
При ошибке `DISPLAY` или `Xauthority` запускайте команду из терминала активного
графического сеанса с его переменными `DISPLAY` и `XAUTHORITY`.
Перед сменой параметров уже запущенного стенда выполните шаг 4.

По умолчанию модель свободна. Она создаётся в исходной позе `stand.d6a`,
с опущенными руками и подошвами на полу.
Приводы используют EffortJointInterface и PD-регуляторы; это настройки симуляции.
Режим `gui --anchored` закрепляет корпус на высоте 0,40 м и применяется
для диагностики интерфейсов. Ходьбу по линии проверяйте только с `--free`.

Направления приводов и нули плеч/локтей приведены к
[физическим наблюдениям](../robot/SERVOS_RU.md#привязка-модели-симуляции-к-физическим-наблюдениям).
Генератор применяет эти поправки при создании URDF, поэтому для уже
запущенного стенда пользователь должен вручную выполнить `stop`, затем
`gui --free` и проверить `status`. Пересборка образа для этих Python-изменений
не требуется. Совпадение направлений и опорных углов проверено офлайн;
устойчивость и контакты новой позы нужно проверить в ручном запуске.

Логи работающего стенда доступны через `bash simulation/sim.sh logs`,
терминал внутри контейнера — через `bash simulation/sim.sh shell`.
Выход из этого терминала командой `exit` оставляет стенд работающим;
для завершения опыта выполните шаг 4.

## ActionGroups

Девять действий линии подготовлены в `simulation/actiongroups`.
Для другого каталога передайте непосредственно папку с файлами `.d6a`:

```bash
bash simulation/sim.sh gui --free --actions-dir /absolute/path/to/ActionGroups
```

Альтернатива — переменная `ROBOTRIO_ACTIONS_DIR`. Каталог монтируется только
для чтения и меняется перезапуском контейнера. По умолчанию калибровка берётся
из `servo_controller.yaml` HiWonder; свой файл можно подключить через
`ROBOTRIO_SERVO_CONFIG=/absolute/path/to/servo_controller.yaml` при запуске.
Преобразование: `angle = (pulse - model_init) / coefficient - initial_angle`,
`coefficient = ±(180 / 3.1415926 / 240 * 1000)`, знак задаёт порядок min/max.
`model_init` берётся из `robotrio_servo_init` в URDF, а при его отсутствии —
из аппаратного `init`. `initial_angle` — смещение встроенного `stand` в свободной
модели; в закреплённой модели оно равно нулю. Аппаратный YAML не изменяется.

```bash
bash simulation/sim.sh list-actions
bash simulation/sim.sh action-info stand
bash simulation/sim.sh action stand
bash simulation/sim.sh action forward_one_step
bash simulation/sim.sh action forward --repeat 3
bash simulation/sim.sh action turn_right --repeat 8 --pause 0.1
bash simulation/sim.sh stop-action
```

Имя передаётся без `.d6a`. На старте GUI группы автоматически не проигрываются.
`action-info` показывает кадры, длительность, сервоприводы и хеш. Проигрыватель
проверяет формат, pulse, карту ID и пределы URDF, не подрезая значения.
Одновременно работает один проигрыватель. Пауза `/clock` прекращает действие
по watchdog. `stop-action` останавливает команды, сохраняя текущие цели суставов;
для остановки физики используйте Pause, для всего стенда — `stop`.
Перед Reset World/Model/Time остановите действие; сброс позы не заменяет остановку.
Группы задают все сервоприводы своих кадров: удержание руки из `tag_grab.py`
в ручном проигрывателе не применяется автоматически.

### Проверка пробных движений правой руки

Файлы [place_right_top_down.d6a](../robot/ActionGroups/place_right_top_down.d6a)
и [retract_right_after_place.d6a](../robot/ActionGroups/retract_right_after_place.d6a)
содержат пробную установку сверху вниз и последующее убирание правой руки.
[Значения и порядок кадров](ACTION_GROUPS_RU.md#пробная-установка-и-убирание-правой-руки)
описаны отдельно. Действия не проверены физически и пока не подключены
к `tag_grab.py`.

Если стенд ещё не работает, запустите его вручную по разделу выше:

```bash
bash simulation/sim.sh gui --free
```

При уже работающем стенде повторный запуск не нужен. Проверьте `status`
и дождитесь `initial_pose_ready: true` без ошибки подготовки. Остановите
другие источники движения перед опытом.

Группы читаются непосредственно из проекта через `--action-path`.
Начальная стойка при этом по-прежнему берётся из обычного каталога `/actions`;
копировать новые файлы или менять `--actions-dir` не требуется.

```bash
bash simulation/sim.sh status
bash simulation/sim.sh action-info place_right_top_down --action-path /workspace/robot/ActionGroups
bash simulation/sim.sh action-info retract_right_after_place --action-path /workspace/robot/ActionGroups
```

После готовности стойки запустите установку (3 секунды симуляции):

```bash
bash simulation/sim.sh action place_right_top_down --action-path /workspace/robot/ActionGroups
```

Осмотрите конечную позу. Из неё запустите убирание (6 секунд симуляции):

```bash
bash simulation/sim.sh action retract_right_after_place --action-path /workspace/robot/ActionGroups
```

Ожидается возврат всех ID 1–22 к целям `stand`. Остановка действия и всего стенда:

```bash
bash simulation/sim.sh stop-action
bash simulation/sim.sh stop
```

В исправленной модели ID 20 сгибает локоть, ID 18 поворачивает предплечье;
имена суставов CAD сохранены. Направления и опорные углы проверены расчётом,
динамическая проверка движений остаётся за пользователем. Куба и паза в сцене
нет, поэтому установку и освобождение реального груза этот просмотр
не подтверждает. В свободном режиме также наблюдайте равновесие модели.

## Камера и следование линии

Сцена содержит ровный пол и чёрную линию шириной 30 мм: дугу длиной 2 м,
радиусом 6 м, с поворотом 19,1°. Кубов и AprilTag-меток в сцене нет.
Overlay крепит камеру к `head_tilt_link`, поэтому движение головы меняет изображение.
Привязка камеры и виртуальная поза 500/300 относятся только к симуляции.
Аппаратный `line_follow.py` голову не двигает; адаптер стенда готовит её перед первым действием.

После подготовки стойки, в отдельных терминалах:

```bash
bash simulation/sim.sh line-view
bash simulation/sim.sh line-follow --image-orientation standard --max-seconds 30
# После проверки ориентации изображения и решений, не более трёх действий:
bash simulation/sim.sh line-follow --execute --empty-hands --image-orientation standard --max-actions 3
```

Для зеркального изображения используйте `mirrored`.
Смещение параллельной линии вызывает приставной шаг, наклон — поворот,
центр — `forward_one_step`. Для решения нужны свежие согласованные кадры;
при потере линии или камеры слепого поиска нет. Дополнительный просмотр
из `shell`: `rosrun rqt_image_view rqt_image_view /camera/image_raw`;
состояния суставов: `rostopic echo -n 1 /joint_states`.
Оставляйте один источник движения. Завершение:

```bash
bash simulation/sim.sh line-stop
bash simulation/sim.sh stop
```

## Ручная проверка и текущее состояние

Для документации достаточно ссылок, команд и diff. Начальную стойку
проверяйте через `status`, камеру и решения алгоритма — командами из раздела
выше. Все проверки, запускающие симуляцию, пользователь выполняет вручную.
Отдельно доступен `bash simulation/sim.sh smoke`: он запускает gzserver/Xvfb
и проверяет модель, время, контроллеры, состояния суставов, камеру и отклик головы;
он не подтверждает свободную ходьбу и захват.

Последний описанный свободный прогон на дуге, 18 октября 2026, не пройден:
завершены 6 шагов вперёд и 2 приставных влево; после начала девятого действия
расстояние от линии достигло 0,08006 м и сработала остановка.
Продвижение вдоль дуги — 0,172 м; падения не было. Исторический результат
75 см относится к прежнему контроллеру на прямой. Более поздние изменения
не подтверждают исправление ухода без нового испытания.

Прибытие к метке Б, полный маршрут, перенос кубов и аппаратный алгоритм линии
не подтверждены. Контакты и динамика модели не откалиброваны по роботу;
рабочие pulse и аппаратную калибровку ради URDF не изменяйте.
Физическая проверка пользователя уточнила назначения локтевых приводов:
ID 17–18 поворачивают предплечья, ID 19–20 сгибают локти. Оси CAD соответствуют
этой структуре, хотя программные имена — `*_el_pitch` и `*_el_yaw` соответственно.
[Измеренные положения и направления](../robot/SERVOS_RU.md#полная-карта-сервоприводов)
применены к направлениям и опорным углам симуляции без изменения аппаратной
калибровки и ActionGroups. Соответствие реальной геометрии захвата, контактов
и динамики требует дальнейшей проверки. Прежние прогоны ходьбы относятся
к модели до этих поправок и не подтверждают поведение новой версии.
История прежних экспериментов сохранена в Git: `simulation/TEST_RESULTS_RU.md`.
