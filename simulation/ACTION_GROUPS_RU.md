# ActionGroups AiNex

Исходные рабочие `.d6a` получены напрямую с робота и подтверждены пользователем
как достоверные и проверенные. Для штатного исполнения через MotionManager
повторная проверка их безопасности и диапазонов не требуется.
[Вызов на роботе](../robot/README.md), [работа в симуляции](README.md).

## Источники и формат

Основной источник: `simulation/artifacts/d6a_from_robot/home/ubuntu/software/ainex_controller/ActionGroups/`.
В нём 48 действий; девять действий линии скопированы в `simulation/actiongroups`.
[Полная инвентаризация](actiongroups_manifest.json), [выборка и SHA256](actiongroups_selection.json).
Архив `simulation/artifacts/ainex_d6a.tar.gz` хранит 98 файлов: 48 основных,
48 резервных из `action_bk` и две записи из `.ros`.
Для восстановления из архива, из корня проекта:

```bash
mkdir -p simulation/artifacts/d6a_from_robot
tar -xzf simulation/artifacts/ainex_d6a.tar.gz \
  -C simulation/artifacts/d6a_from_robot
```

Пути резервных файлов в manifest относятся к первоначальной инвентаризации;
локально они могут присутствовать только в архиве.
Рабочий каталог не следует автоматически заменять версиями из `action_bk`:
`left_shot`, `right_shot`, `temp` отличаются. Основные `calib` и `temp` совпадают.

Все 48 основных файлов — SQLite с таблицей `ActionGroup` и столбцами
`Index`, `Time`, `Servo1`…`Servo22` в этом порядке. `Time` — целые миллисекунды,
servo-значения — целые pulse. Индексы уникальны, порядок хранения совпадает
с порядком индексов. MotionManager читает `SELECT *` и назначает ID по позиции
столбца: каждый кадр отправляет все 22 команды, пропуска отдельных ID нет.
Головы ID 23/24 в этих группах нет.

## Движения, используемые проектом

| Имя | Кадры | Время кадров, с |
| --- | ---: | ---: |
| `stand` / `walk_ready` | 1 / 1 | 1,00 / 0,50 |
| `forward_one_step` / `forward` | 6 / 4 | 1,20 / 0,72 |
| `move_left` / `move_right` | 4 / 4 | 0,80 / 0,80 |
| `turn_left` / `turn_right` | 4 / 4 | 0,78 / 0,82 |
| `back_step` | 4 | 0,90 |
| `clamp_left` / `clamp_right` | 7 / 8 | 4,40 / 6,10 |
| `place_block` | 24 | 10,52 |
| `left_hand_put_block` / `right_hand_put_block` | 10 / 10 | 4,50 / 4,50 |

Длительность кадров не задаёт расстояние или угол перемещения.
`forward_step` отличается от `forward_one_step`; `go_turn_left/right` — от
`turn_left/right`. При выборе группы используйте её точное имя.
Ходьба и повороты также задают руки; в выбранных группах линии захваты ID 21/22
получают 500. Сохранение занятой руки требует соответствующей логики сценария.
Новые `robot/ActionGroups/place_block_left.d6a` и `place_block_right.d6a`
и их начальные позы описаны в [руководстве робота](../robot/README.md#размещение-куба-одной-рукой).

## Пробная установка и убирание правой руки

[place_right_top_down.d6a](../robot/ActionGroups/place_right_top_down.d6a) и
[retract_right_after_place.d6a](../robot/ActionGroups/retract_right_after_place.d6a)
подготовлены для ручной проверки в симуляции. Это новые пробные действия,
а не исходные проверенные ActionGroups робота. На физическом роботе они
не испытывались; наблюдавшиеся рабочие положения не подтверждают полные
механические пределы.

База всех кадров — последний кадр исходного `stand.d6a` с робота.
Его значения правой руки: ID 14 = 165, 16 = 170, 18 = 500, 20 = 850,
22 = 500. Все кадры содержат `Servo1`…`Servo22`: ноги, левая рука и ID 18
во всех кадрах получают значения `stand`. Поэтому эти файлы не сохраняют
произвольную текущую позу остальных конечностей. Голова ID 23–24 не задаётся.
Калибровочный `init` и измеренные показания исходной позы вместо команд
`stand` не подставлялись. Исходные группы не изменены.

### Установка `place_right_top_down`

Три кадра по 1000 мс, всего 3 секунды. Пробный верхний ориентир плеча
ID 14 выбран как 425: на 150 pulse вперёд от наблюдавшегося положения
275 «плечо параллельно телу». Последний переход 425 → 275 опускает руку
по дуге вращения плеча; прямолинейная вертикальная траектория кисти
не рассчитывается. Это начальный вариант для последующей коррекции.

| Кадр | ID 14 | ID 16 | ID 20 | ID 22 | Действие |
| ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 165 | 170 | 850 | 610 | Поза тела `stand`, захват в положении удержания |
| 2 | 425 | 170 | 850 | 610 | Поднять руку движением плеча вперёд |
| 3 | 275 | 170 | 850 | 610 | Опустить руку; сохранить положение захвата |

### Убирание `retract_right_after_place`

Начальная поза должна соответствовать концу `place_right_top_down`.
Шесть кадров по 1000 мс, всего 6 секунд. При запуске из другой позы первый
кадр также приведёт все заданные суставы к своим абсолютным целям.

| Кадр | ID 14 | ID 16 | ID 20 | ID 22 | Действие |
| ---: | ---: | ---: | ---: | ---: | --- |
| 1 | 275 | 170 | 850 | 650 | Открыть правый захват |
| 2 | 275 | 170 | 900 | 650 | Согнуть локоть до пробного рабочего положения |
| 3 | 275 | 320 | 900 | 650 | Отвести плечо от тела на +150 от `stand` |
| 4 | 165 | 320 | 850 | 650 | Одновременно вернуть локоть и плечо вперёд/назад в `stand` |
| 5 | 165 | 170 | 850 | 650 | Вернуть боковое положение плеча в `stand` |
| 6 | 165 | 170 | 850 | 500 | Вернуть захват в `stand` |

Итоговый кадр полностью совпадает с исходным `stand` для всех ID 1–22.
ID 20 = 850 соответствует наблюдавшемуся прямому углу локтя, а не его
полному разгибанию. В кадре 4 команды ID 14 и 20 входят в одно сообщение
с общей длительностью.

Порядок ручного запуска приведён в
[руководстве симуляции](README.md#проверка-пробных-движений-правой-руки).
В исправленной модели ID 20 связан с поперечным сгибом `r_el_yaw`,
ID 18 — с продольным поворотом `r_el_pitch`. Названия CAD сохранены,
ID местами не переставлялись. Направления осей и опорные положения плеч
и локтей согласованы с [наблюдениями на роботе](../robot/SERVOS_RU.md#привязка-модели-симуляции-к-физическим-наблюдениям).
Текущая сцена не содержит куба и паза: просмотр не подтверждает установку,
освобождение груза или отсутствие столкновений на реальном макете.

## Записи и ограничения симулятора

`.ros/walk.d6a` и `.ros/walk1.d6a` — отдельные записи с числами до 217166,
не соответствующими формату pulse 0…1000. Не подключайте `.ros` как рабочий
каталог действий и не исправляйте эти записи автоматически.
Синтетические `inspection_{head,invalid,long}.d6a` использовались для
проверки проигрывателя; они не входят в исходные движения робота.

Строгий симуляционный проигрыватель отклоняет команды вне текущих
URDF-пределов до движения. Совместимость конкретной группы зависит
от применённых направлений, нулей модели и её пределов.
Это ограничение модели, а не свидетельство недостоверности аппаратных групп.
Pulse, файлы и рабочую калибровку ради прохождения симуляции не подрезайте.
